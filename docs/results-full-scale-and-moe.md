# Full-scale baselines, Gate 1, and the two-expert MoE

> **Status:** complete, single seed
> **Date:** 2026-08-11 · RTX 5070 Ti · torch 2.9.1+cu128 · Ultralytics 8.4.115
> **Corpus:** `data/dior_hbb_full` — DIOR clear (23,463) + Hazy-DIOR fog (23,385 ids × 3 severities)
> **Raw numbers:** `docs/benchmarks.md` (regenerated by `scripts/collect_benchmark.py`)

Everything here is horizontal boxes. Every arm uses identical hyperparameters —
100 epochs, 5,862 training images per epoch, 2,000 validation images, batch 16,
640 px, `optimizer: auto`, cosine LR, seed 0, COCO-pretrained `yolo11n.pt`.
Only the training condition and the model architecture differ. Test splits are
never subsampled.

---

## 1. Gate 1 — passed

| | value |
|---|---|
| **VOC07 mAP@0.5** | **65.2** |
| COCO mAP50 | 69.8 |
| COCO mAP50-95 | 49.5 |

Against the reference committed *before* training (`gate1-reference.md`):
**+8.1 over YOLOv3/Darknet-53 (57.1)**, and 0.9 below the published ceiling
(66.1, RetinaNet-R101 and PANet-R101).

19 of 20 classes score AP50 > 0.5 and none fall below 0.2, so the mAP is carried
by the whole taxonomy rather than by a few easy classes — which is what the gate
was actually testing. Two caveats belong with any citation of 65.2: we train on
5,862 images where the published numbers use 11,725 (val is held back for
checkpoint selection), and YOLO11n is 2.6 M parameters against Darknet-53's
~62 M. The gap is six years of detector progress plus COCO pretraining, not a
better experimental setup.

**The pipeline is confirmed sound.** Corpus, label conversion, splits and both
metric implementations work end to end.

## 2. The interference test — the result that matters

Each specialist scored on its own condition, against the dense union model
trained on both. All on the full test split, COCO mAP50.

| Condition | Specialist | Union (dense) | Δ (specialist − union) |
|---|---:|---:|---:|
| clear | 0.6984 | 0.6760 | **+0.0225** |
| fog | 0.6594 | 0.6589 | **+0.0005** |

`05-experiment-plan.md` sets ~2 points as the single-seed noise floor. On clear
the deficit is 2.25 points — right at that boundary. On fog it is **0.05 points,
which is nothing at all**.

This is the premise of condition-routed MoE, tested directly: a dense model
trained on the union of conditions gives up essentially nothing on fog relative
to a dedicated fog specialist. **There is no interference for routing to
recover.** An architecture whose entire purpose is to separate mutually
interfering representations has, on this corpus, almost nothing to separate.

### The asymmetry underneath it

| Trained on ↓ / tested on → | clear | fog |
|---|---:|---:|
| clear specialist | 0.6984 | 0.5430 |
| fog specialist | 0.6646 | 0.6594 |
| union (dense) | 0.6760 | 0.6589 |

The matrix is strongly asymmetric. The clear-trained model loses 15.5 points
under fog. The fog-trained model loses **nothing** on clear — it scores 0.6646
there, slightly *above* its own fog score. Training on haze buys clear
performance for free; training on clear does not buy haze performance.

That asymmetry, not routing, is the actionable finding: for this corpus the
efficient answer is to train one model on degraded data, not to build a router.

## 3. rPC — robustness retention

`rPC = mAP_fog / mAP_clear` for the same model. This is the one quantity that
can be set beside published results, because a ratio cancels the box-format and
metric-convention differences that make their absolute mAP uncomparable
(`comparison-baselines.md`).

| Model | clear | fog | rPC |
|---|---:|---:|---:|
| clear specialist (ours) | 0.6984 | 0.5430 | **77.7 %** |
| union dense (ours) | 0.6760 | 0.6589 | 97.5 % |
| MoE @ neck (ours) | 0.6734 | 0.6567 | 97.5 % |
| MoE @ backbone (ours) | 0.6717 | 0.6532 | 97.2 % |
| fog specialist (ours) | 0.6646 | 0.6594 | 99.2 % |
| — | | | |
| NIRNet (published) | 63.5 | 40.8 | 64.3 % |
| MPRNet (published) | 64.7 | 41.5 | 64.1 % |
| Oriented R-CNN (published) | 62.66 | 38.70 | 61.8 % |

**The only row comparable to the published ones is the clear specialist at
77.7 %**, because those papers train on clean imagery and evaluate zero-shot on
hazy. Every other row here was trained on fog, which is a strictly easier
problem and cannot be set against them.

77.7 % vs NIRNet's 64.3 % is a large gap and should be treated with suspicion
rather than celebrated. Three reasons it is not a like-for-like win:

1. **Different degradation.** NIRNet's Hazy-DIOR is cloud corruption with
   per-image random transparency; the release we hold ships three fixed haze
   severities. We have no evidence the severities are equally hard.
2. **Different evaluation set.** They report on 11,738 DIOR-R images with
   oriented boxes; we report on 124,442 HBB instances across 11,738 clear and
   35,112 fog images.
3. **Pretraining.** Our backbone is COCO-pretrained; robustness transfer is
   exactly the kind of thing that benefits from it.

The defensible statement is that rPC is measurable in this pipeline and lands in
a plausible range — not that we beat NIRNet.

## 4. The MoE arms

Two experts (clear / fog), image-level top-1 hard routing, heterogeneous 3×3 and
5×5 kernels, residual and zero-initialised. Both arms train on the **same union
corpus as the dense baseline** — verified by identical `data_sha_train`
(`e83d68c8279d`), which is what makes this comparison valid.

| Tested on | Dense | MoE @ backbone | MoE @ neck |
|---|---:|---:|---:|
| union | 0.6626 | 0.6576 (−0.0050) | 0.6609 (−0.0017) |
| clear | 0.6760 | 0.6717 (−0.0043) | 0.6734 (−0.0026) |
| fog | 0.6589 | 0.6532 (−0.0057) | 0.6567 (−0.0022) |

**The MoE does not beat the dense baseline on any condition.** Every cell is
slightly below it, by 0.2–0.6 points — far under the 2-point noise floor, so the
honest reading is *no significant difference*, not *slightly worse*.

**Placement:** the neck is consistently better than the deep backbone, on all
three cells. It is also the cheaper of the two in parameters. If the design is
pursued further, the neck is the position to pursue it in.

### Cost

| Model | Params | GFLOPs | b1 latency | b1 FPS | b16 ms/img |
|---|---:|---:|---:|---:|---:|
| dense | 2,593,740 | 6.52 | 8.82 ms | 113.3 | 0.728 |
| MoE @ backbone | 3,524,686 (+36 %) | 7.36 | 8.78 ms | 113.8 | 0.758 |
| MoE @ neck | 2,861,294 (+10 %) | 8.96 | 9.46 ms | 105.7 | 0.961 |

Measured on an idle GPU, batch composition stated, router cost included.

**The efficiency argument does not survive contact with measurement.** The MoE
arms are larger and, at the neck, slower — 105.7 FPS against 113.3 — while
matching the dense model on accuracy. The reason is structural: at N=2 with
top-1 you skip one expert's compute, but you add a gate, dispatch and combine
overhead, and the MoE block is more expensive than the `C3k2` it replaced.
`06-moe-design-guide.md` §1.1 rests the efficiency case on total parameters
growing while per-example FLOPs stay flat; with two experts there is not enough
parameter growth for that trade to pay.

Note the GFLOPs figures are **dense-equivalent** — thop traces both expert
branches. Only one runs per image, so true activated compute is lower than
shown; the latency column is the number to trust.

### Router collapse, and the fix

The first MoE run collapsed: expert 0 fell to a **0.000 dispatch share by epoch
2**. The cause is the zero-initialisation that makes the block an identity at
step 0 — both experts produce identical outputs, so the argmax is decided by
gate noise, the winner takes all the gradient, and the lead compounds.

Fixed with noisy top-k routing (`06 §2.4`): Gaussian noise on the gate logits
during training only. Min-expert share at initialisation, over 5 fresh blocks:

| noise_std | min-expert share |
|---|---|
| 0.0 | 0.047, 0.188, 0.344, 0.359, **0.000** |
| 1.0 | 0.453, 0.453, 0.469, 0.484, 0.406 |

Both trained arms then held balanced routing for all 100 epochs (backbone min
share 0.392, neck 0.247). Eval-time routing is deterministic, and the auxiliary
loss and logged utilisation read the clean logits so the statistics describe the
router rather than the noise.

**A second finding worth recording:** during the collapse, the entropy auxiliary
loss read ≈0.001 — "balanced". Entropy over the batch-mean *soft* gate
distribution cannot see hard-assignment collapse. The `switch` loss weights by
dispatch fraction and does better, but has its own blind spot (at exactly uniform
gate probabilities the dispatch split is invisible, since the fractions sum to
1). Both facts are asserted in `tests/test_moe.py`. **Neither auxiliary loss can
be trusted alone to reveal a dead expert; the utilisation histogram is
mandatory**, exactly as `06 §3.3` insists.

## 5. What this means for the thesis

Read against `01-scope-and-claim.md`:

- **C1 (efficiency)** is not supported at N=2. The routed model is bigger and no
  faster. It could only become supportable against a restoration cascade (B4),
  which has not been run.
- **C2 (interference)** is **not supported on this corpus**. The dense union
  model gives up 0.05 points on fog against a dedicated fog specialist. This is
  the claim the plan warned was "the most expensive to prove and the easiest to
  fail", and it failed cheaply and early rather than in month 8.
- **C3 (router robustness)** is the one still standing, and the infrastructure to
  study it now exists: balanced routing, per-epoch utilisation, deterministic
  eval routing, and a measurable rPC.

The fallback in `01-scope-and-claim.md` — "condition-specialized routing does not
improve degraded-condition RS detection under matched compute, and here is why" —
is currently the result the evidence supports, and it is reported as such.

### Honest limitations

1. **Single seed.** Every difference discussed here is below the 2-point noise
   floor the plan itself sets. Three seeds on the main comparison are required
   before any of it is quotable.
2. **One degradation.** Fog only. Low illumination was out of scope for this
   round, so "two experts" means clear/fog, and the interference result may not
   generalise to a condition pair that genuinely conflicts.
3. **Synthetic haze, and only three severities.** The release ships fixed
   severity tiers rather than randomized parameters — the monoculture risk
   `03-datasets.md` flags as fatal-if-unaddressed. No real-haze test set was
   evaluated.
4. **An encoding confound.** In the full corpus clear is 100 % JPEG while fog is
   89 % PNG, and the difference is compression *history*, not container, so
   re-encoding cannot remove it. It does not affect the baselines, but a router
   keyed on high-frequency statistics could exploit it. Recorded per-image in
   `manifest.csv`.
5. **Matched-budget fog.** Fog has 17,505 training images available and was
   given 5,862 to match the other arms. A fog arm trained on everything would
   score higher and be uncomparable.

### The next experiment this points to

Not a bigger MoE. The interference matrix says the useful question is why
fog-trained generalises to clear while clear-trained does not, and whether that
asymmetry survives a second degradation. If it does, the efficient design is one
model trained on degraded data — and the thesis contribution shifts to
characterising *why*, which is claim C3's territory.

## 6. Reproducing

```bash
python scripts/recover_ids.py                       # ~25 min, cached artefact
python scripts/prepare_dataset.py --scope full      # clear + fog corpus
python scripts/make_union.py --scope full           # balanced union corpus
python scripts/install_moe.py                       # register MoEBlock

python scripts/train.py --config configs/train/clear_full_yolo11n.yaml
python scripts/train.py --config configs/train/fog_full_yolo11n.yaml
python scripts/train.py --config configs/train/union_full_yolo11n.yaml
python scripts/train.py --config configs/train/moe_backbone_yolo11n.yaml
python scripts/train.py --config configs/train/moe_neck_yolo11n.yaml

python scripts/run_evaluations.py                   # all 13 cells
python scripts/benchmark_speed.py                   # idle GPU only
python scripts/collect_benchmark.py --out docs/benchmarks.md
```

Every run is in MLflow (`outputs/mlruns`, experiment `dior-hbb-full`) with
per-epoch losses and metrics, per-class AP, speed, parameter counts, expert
utilisation, and dataset/model content fingerprints.
